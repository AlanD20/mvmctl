# Sudo Privilege Architecture: Group-Based Passwordless Access

**Status:** Superseded for v0.3.0 by
[ADR-0016: Root-Owned Single-Binary Privileged Dispatch](0016-root-owned-single-binary-privileged-dispatch.md)
**Date:** 2026-05-22
**Last Updated:** 2026-06-20 (Go implementation complete)

> **Replacement accepted, implementation in progress:** ADR-0016 replaces the user-owned wildcard sudo design with one
> root-owned system installation and an early typed privileged dispatcher. The system installer and no-action dispatcher
> foundation are implemented. Raw tool grants and the public-CLI wildcard below remain transitional until Tasks 4-14 and
> the L2 release gate pass; they must not be described as the final security boundary.

The project uses a **tightly scoped, group-based sudo model** where members of a dedicated Unix group (`mvm`) can execute specific privileged commands via `sudo` without a password prompt. This avoids running the entire CLI as root while still allowing VM creation (loop-mount), network management (ip/iptables/nft), kernel module loading (modprobe), and sysctl configuration.

## The Group Activation Mechanism

`sg mvm` (switch group) changes the **primary GID** of the current process to the `mvm` group. This is visible in `id` output:

```
$ sg mvm -c 'id'
uid=1000(www) gid=957(mvm) groups=957(mvm),98(power),961(docker),...,1001(www)
```

Key implications:
- `os.Getuid()` returns 1000 (not root), so `IsRoot()` is false and `sudo` IS prepended by `SpawnService()` or the `loopmount` backend's `runWireOp()`
- `SessionHasGroup()` (`internal/lib/system/privilege.go`, line 135) checks process GIDs via `os.Getgroups()`/`os.Getgid()`/`os.Getegid()`
- The primary GID changes from the user's normal group to mvm
- The supplementary group list preserves membership in ALL other groups

## The Actual Sudoers File

`mvm host init` creates `/etc/sudoers.d/mvm` (path resolved by `infra.SudoersDropInPath()`). In the current development
baseline, the file is generated by `GenerateSudoersContent()` with the fixed root-owned system path:

```
%mvm ALL=(root) NOPASSWD: /usr/sbin/ip, /usr/sbin/iptables, /usr/sbin/iptables-restore, /usr/sbin/iptables-save, /usr/sbin/nft, /usr/sbin/sysctl, /usr/sbin/modprobe, /usr/local/bin/mvm *
```

The sudoers file is generated by `GenerateSudoersContent()` using two sources from `internal/infra/constants.go`:

- **`PrivilegedBinaries`** — system binaries with hardcoded absolute paths (declared as `map[string]string` with package names, plus `PrivilegedBinariesOrdered` for deterministic ordering):
  - `/usr/sbin/ip` (iproute2)
  - `/usr/sbin/iptables` (iptables)
  - `/usr/sbin/iptables-restore` (iptables)
  - `/usr/sbin/iptables-save` (iptables)
  - `/usr/sbin/nft` (nftables)
  - `/usr/sbin/sysctl` (procps)
  - `/usr/sbin/modprobe` (kmod)

- **Service binary (transitional)** — fixed `/usr/local/bin/mvm *` for privileged public service subcommands. Task 14
  replaces this wildcard with only `/usr/local/bin/mvm __mvm_privileged_v1 *` after every caller is typed.

NOTHING else is permitted. `sudo -n true`, `sudo cat /etc/sudoers.d/mvm`, `sudo test -f ...`, and any other non-listed command WILL prompt for a password. This is by design and is NOT a configuration problem.

## How VM Creation Encapsulates Privileged Work

All loop-mount operations are delegated to `mvm run provision`. Trusted Firecracker release installation, jail mounts, cleanup, and Jailer execution are delegated to `mvm run jailer`. Both reuse the single approved `mvm` sudoers entry instead of granting direct sudo access to dynamic binaries or mount tools.

The loop-mount call chain is:

```
mvm vm create
  → ImageProvisioner uses loop-mount backend (not guestfs)
  → LoopMountBackend.Run() calls runWireOp() (internal/lib/provisioner/loopmount/backend.go, line 188)
       → runWireOp() resolves the current binary; supported host operation runs `/usr/local/bin/mvm`
       → Prepends "sudo" to args when !system.IsRoot()
       → system.DefaultRunner.Run(ctx, ["sudo", mvmPath, "run", "provision"], ...)
            ↑ sudoers allows %mvm to run mvm without password
            ↑ mvm is now running as root (for the provision subcommand)
               → Inside provision: losetup, mount, umount, etc. — all as root
```

Alternatively, when using `system.SpawnService()` (for `SpawnConfig{Privileged: true}`), the sudo wrapper is applied inside `internal/lib/system/spawn.go`:

```go
if cfg.Privileged && !IsRoot() {
    cmd = exec.Command("sudo", exe, "run", cfg.Name)
}
```

This means:
- The sudoers file does NOT need `losetup`, `mount`, `umount`, `mkfs.ext4`, `blkid`, or any filesystem tool
- ALL filesystem operations are encapsulated in the compiled `mvm` binary's `run provision` subcommand
- The `mvm` binary is the single sudoers entry point for VM creation
- Jailer and Firecracker execute only from root-owned trusted release paths; users still invoke `mvm` without sudo

## How System Tests Interact with Sudo

When running `sg mvm -c 'pytest tests/system/'`:

1. `sg mvm` sets the process primary GID to `mvm` (957)
2. The pytest process inherits `mvm` as its primary group
3. All subprocesses spawned by tests inherit the `mvm` primary group
4. When `mvm vm create` calls the loopmount backend's `runWireOp()`:
   - `CheckPrivileges()` (internal/lib/system/privilege.go) checks: group exists ✅, user in group ✅, session has group ✅
   - `runWireOp()` sees `!system.IsRoot()` → prepends `sudo`
   - The sudoers drop-in grants NOPASSWD access
   - The command executes as root without any password prompt

## Why Not Run Everything as Root

- **Principle of least privilege (target).** The CLI runs as a normal user for HTTP downloads, file I/O, SQLite queries,
  and non-privileged operations. The transitional raw-tool and public-CLI grants remain broader than the named effects
  accepted by ADR-0016 and are removed only at Task 14, after Tasks 8–13 migrate every caller.
- **Known transitional exposure.** Root ownership prevents replacement of the authorized executable, but
  `/usr/local/bin/mvm *` still exposes broad public argument handling as root. A compromise of the ordinary CLI process
  must be treated as potentially reaching that authority until typed callers and the marker-only policy replace it.
- **Development ergonomics.** Developers build and iterate as a normal user. Installing/upgrading the trusted system
  image and machine-global `host init` remain explicit administrator operations.

## Why a Group-Based Model

- The `mvm` group cleanly separates "can manage VMs" from "can't manage VMs" at the OS level
- `sg mvm` activates the group for the current shell session without requiring logout/login, CI restart, or environment manipulation
- System tests run under `sg mvm -c 'pytest ...'`, inheriting the group across all subprocesses at zero cost
- Initial setup is two explicit administrator steps: `sudo <trusted-mvm-binary> host install-system`, then
  `sudo /usr/local/bin/mvm host init`.

## Consequences

- `sudo -n true`, `sudo -v`, and any non-listed command will fail for `mvm` group members. The `CheckPrivileges()` function is aware of this and does NOT gate privileged execution on credential validation — it gates on group membership and session group activation.
- Adding a new privileged binary requires updating `internal/infra/constants.go` (add to `PrivilegedBinaries` and `PrivilegedBinariesOrdered`) AND regenerating the sudoers file via `mvm host init`.
- The root-owned binary MUST exist at `/usr/local/bin/mvm`. User cache cleanup does not remove it; reinstall it only from
  a trusted artifact through `host install-system`.
- The group name is defined as `MVMUnixGroup = CLIName` (`internal/infra/constants.go`, line 39). Currently `CLIName = "mvm"`, so the group is `mvm`.
- `sg mvm` is a prerequisite for VM-related system tests. Non-VM tests work without it.
- Tests that involve VM creation MUST verify the `mvm` group is active before attempting to create VMs.
