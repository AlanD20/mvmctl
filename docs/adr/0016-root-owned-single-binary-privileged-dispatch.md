# Root-Owned Single-Binary Privileged Dispatch

**Status:** Accepted — implementation in progress
**Date:** 2026-08-20
**Last Updated:** 2026-09-13 (sudoers publication, retained outputs, private status, and raw data volumes)
**See also:** [ADR-0002: Single Go Binary Architecture](0002-single-go-binary-architecture.md),
[ADR-0005: Sudo Privilege Architecture](0005-sudo-privilege-architecture.md),
[ADR-0015: Jailer Is the Canonical Firecracker Launcher](0015-jailer-canonical-launcher.md), and
[ADR-0017: Per-VM Network Namespaces and Typed Connectivity Policies](0017-per-vm-network-namespaces-and-typed-policies.md)

## Context

mvmctl is a Go CLI whose user-facing commands and subprocess services are compiled into one release artifact. The CLI
is intended to run as an unprivileged user while a small set of VM, filesystem, network, firewall, cgroup, and Jailer
operations require root.

The existing installation contract puts `mvm` at user-owned `~/.local/bin/mvm` and generates a passwordless sudoers
entry for that path with wildcard arguments. A member of the `mvm` group can replace the executable and then ask sudo to
run the replacement as root. Root ownership checks performed later by Jailer cannot repair a compromised executable
boundary.

The existing sudoers policy also grants raw argument access to host tools such as `ip`, `iptables`, `nft`, `modprobe`,
and `sysctl`. Those tools expose substantially more host authority than the named mvmctl operations that need them. The
policy therefore does not provide the targeted access claimed by ADR-0005.

Introducing a separately compiled privileged helper would provide a small executable trust boundary, but it would break
the project's single-binary product contract. A safe design must retain one artifact without allowing the ordinary CLI
initialization path or caller-controlled program bytes to execute as root.

## Decision

### One root-owned system installation

Manually built and release-script artifacts are installed at `/usr/local/bin/mvm` as `root:root`, mode `0755`. The
directory chain must be root-owned and not group/world writable. `/usr/bin/mvm` is reserved for a future installation
owned by a distribution package manager.

Normal users execute `/usr/local/bin/mvm` without sudo. The file contains both the public CLI and the internal privileged
dispatcher, preserving one release artifact and one installed executable. Replacing or upgrading the system executable
is an explicit administrator action; a normal user update cannot overwrite it.

Development builds may exist elsewhere, but they are never sudo targets. A development build that needs privileged
operations calls the compatible system installation and fails closed on a privileged-protocol mismatch.

### Administrator bootstrap and system-binary replacement

System installation is selected by the exact `host install-system` command before `app.Initialize()`, Cobra, signal
setup, user configuration, the user database, cache resolution, logging configuration, or service construction. The
bootstrap route clears the inherited environment, installs only fixed root-safe values, and then atomically copies the
running image to `/usr/local/bin/mvm`. Flags and extra arguments are rejected inside the same reserved route and cannot
fall through to the ordinary CLI.

The installer cannot prove whether an already-root process reached it through password-authenticated administrator sudo
or an unintended passwordless rule. It therefore inspects the project-managed sudoers drop-in before touching the
executable and refuses unrecognized active syntax. On a clean host, an administrator runs
`sudo <trusted-mvm-binary> host install-system` and then runs `sudo /usr/local/bin/mvm host init`. Installation is not an
implicit side effect of `host init`.

v0.3.0 does not use this installer to convert, adopt, or preserve a pre-v0.3 installation. Operators must remove the old
managed sudoers rule and clean the old runtime/state layout in an authenticated administrator session before installing
v0.3.0. Later replacement of an already-v0.3-compatible system binary remains an explicit administrator action and
must fail closed when the privileged protocol is incompatible.

Replacing the executable is descriptor-relative, no-follow, temporary-file plus file fsync plus rename plus directory
fsync. Failures after rename report that replacement occurred and whether directory durability is uncertain. A normal
`self-update` may update a user-owned artifact, but it refuses to overwrite the system installation and prints the
administrator bootstrap instruction.

Implementation note (2026-09-13): `ConfigureSudoers` verifies the canonical system executable before admitting the
fixed root-owned directory chain and bounded one-link `0440` policy. It checks required tools, sends generated bytes
to `/usr/sbin/visudo -c -f -` through the standard runner with a 15-second timeout, bounded output, and a fixed
environment, then publishes a descriptor-relative candidate by file fsync, atomic rename, and directory fsync.
Failures preserve replacement, uncertain durability, and cleanup evidence. Existing transitional grants remain exact;
this does not enable the marker-only policy or complete administrator init/reset.

### Host administration admission and reset

Administrator mutation and operator dispatch share the fixed root-owned host journal lock.
Operator requests retain a shared admission lease, check the durable enabled state, and recheck
operator authorization after acquiring that lease. The lease covers dispatch and cleanup, including
retained sessions. Administrator init/reset takes the exclusive lease; acquisition is cancellable
and bounded. Initialization enables admission only after completing the journaled setup.

Reset must retain the Jailer global inventory guard, then the network/global firewall guard, and
prove every owner's managed runtime state cleaned or absent before disabling admission and restoring
the recorded host state. It does not force-stop VMs. Queued requests cannot proceed on their earlier
authorization after reset; they must acquire shared admission and observe the disabled state.
Incomplete rollback retains disabled admission and its journal for explicit administrator retry.

Restoration compares exact recorded group identity, membership, applied sudoers bytes, and managed
settings; it preserves administrator changes rather than treating the old snapshot as unconditional
overwrite authority. Marker-only sudoers is a reset prerequisite: transitional raw-command grants
can bypass dispatcher admission and therefore cannot establish global quiescence. Missing or
malformed admission state refuses operator requests; only explicit administrator initialization can
publish enabled state. This is an implementation contract, not a completed qualification claim.

### Early privileged dispatch

`cmd/mvm/main.go` recognizes one reserved, versioned privileged marker before signal setup, `app.Initialize()`, Cobra,
user configuration, the user database, logging configuration, or plugin/service discovery. Once selected, this path can
only enter the privileged dispatcher; it cannot return to or invoke an ordinary CLI command.

The dispatcher:

- requires effective UID 0 and derives the invoking identity from sudo's trusted execution context;
- verifies the system executable and its directory chain are root-owned and not group/world writable;
- verifies that the invoking user is currently authorized by the `mvm` group;
- sanitizes its environment and uses absolute paths for root-side subprocesses;
- accepts only a versioned, bounded, typed request for a named operation;
- rejects unknown actions, extra arguments or fields, invalid identifiers, unsupported versions, and unchecked paths;
- never accepts raw commands, arbitrary argv, shell fragments, raw firewall syntax, or raw cgroup key/value input.

The sudoers entry may contain a wildcard after the reserved marker because operation arguments vary, but that wildcard
can reach only the early dispatcher. It cannot select the public CLI. The dispatcher remains the authoritative
allowlist, and every handler performs exact argument-count and type checks before side effects.

Synchronous actions return one bounded, versioned response envelope on their control channel. Success payloads are
action-specific. Failures preserve the original `DomainError` code, class, entity, and bounded partial-state details so
the normal-user client can make safe retry and recovery decisions. Logs and subprocess exit status are diagnostic only;
they never replace the structured result or turn a malformed/missing response into a generic successful operation.

The control channel is one full-duplex Unix stream socket duplicated onto file descriptor 0 across `sudo -n`. File
descriptor 0 is control-only and is marked close-on-exec before any handler can launch a descendant. Standard output and
standard error are never parsed as authority. VM console input/output must use a separate typed relay owned by the launch
implementation; it cannot reuse the control channel. Using descriptor 0 avoids sudo policy for inherited descriptors,
while the socketpair permits the client to upload a bounded release archive and receive an early rejection concurrently.
Root requires descriptor 0 to be an `AF_UNIX` `SOCK_STREAM` socket and requires its Linux `SO_PEERCRED` UID/GID to match
the authenticated sudo caller. The peer PID is positive and audit-only; it is not an authorization identity. The
production receiver owns `os.Stdin` directly and accepts no alternate reader or descriptor from its entry point.

The transport always executes exactly
`/usr/bin/sudo -n -- /usr/local/bin/mvm __mvm_privileged_v1 <fixed-action>`. It never uses `PATH`, `os.Executable`, the
current user binary, a caller-supplied executable/argv/environment/cwd/timeout, or a root-EUID bypass; the receiver
requires authenticated non-root sudo identity. `internal/lib/system` provides one concrete transport rather than
extending the generic command runner. Each capability package owns a minimal private `Exchange` interface and named
typed public methods; no public generic privileged call/action/decoder hook is introduced. Hermetic tests inject private
process dependencies and use a dedicated fake exchanger without extending `CommandRunner`, `RunCmdOpts`, `SpawnConfig`,
or the existing `FakeRunner`.

Each request starts with fixed `MVMREQ01` magic, a network-order 32-bit JSON-header length, and a network-order 64-bit
payload length. The strict header is at most 64 KiB and contains schema version 1, the action repeated from argv, and the
action-specific body. The action is 1 through 64 ASCII bytes, starts with an ASCII alphanumeric byte, and thereafter
contains only ASCII alphanumeric bytes, `.`, `_`, or `-`; the caller and receiver enforce the same grammar. The repeated
action must match. Only release install may carry a payload: either zero bytes or an exact stream of at most 128 MiB.
The caller half-closes its write side after the declared bytes, and root requires EOF so truncation or trailing bytes
fail closed before extraction, canonical publication, or promotion of unadmitted bytes. Anonymous staging may occur
while the declared stream is read. Zero-payload operations require EOF before effects.
Authentication, framing, and header failures may return an early error without draining an advertised payload; the
concurrent client treats the resulting uploader `EPIPE` as expected once it has a valid response. The request-header
read deadline is a fixed five seconds, and the release-install archive-payload read deadline is a fixed five minutes.
Each uses the earlier current context deadline when one exists. These are non-configurable security policy; the
receiver reads no second request and does not accept a caller-selected timeout.

Each response starts with fixed `MVMRES01` magic and a network-order 32-bit JSON length followed by at most 64 KiB of
strict schema-version-1 JSON. It contains the matching action, a closed `success` or `error` status, and exactly one typed
result or error. Error envelopes carry code, stable string class, message, operation, entity, and normalized details;
they never serialize wrapped causes, stacks, stderr, or arbitrary Go values. Wire details permit only bounded booleans,
strings, signed integers, and string arrays. Unsupported details are omitted visibly. Root half-closes the control
socket's write side after the complete frame, so the client can validate response EOF independently of process exit. An
error response delivered after all effects and cleanup exits successfully at the process layer. The codec returns a
decoded success/error outcome separately from protocol failure, so a valid root `DomainError` cannot be mistaken for a
malformed frame. A start failure has known no-effect status; any started process with a missing, malformed, truncated,
mismatched, oversized, or non-EOF response returns `CodeProcessError` with `process_started: true` and
`outcome_unknown: true`.

Every success or error response establishes its fixed five-second absolute write deadline immediately before delivery
and uses the earlier current context deadline when one exists. A valid long-running effect therefore does not consume
the response-write budget. Final error-envelope delivery computes that absolute deadline before applying
`context.WithoutCancel`; it never gains a fresh or unbounded interval after cancellation is detached. The
request-header, archive-payload, and response-write limits are compiled, non-configurable security policy.

The receiver rejects an initially nonblocking fd 0. Response writes do not depend on mutable shared file-status flags:
they use raw `SendmsgN` with `MSG_DONTWAIT|MSG_NOSIGNAL` and bounded `POLLOUT` waits against the already-established
absolute deadline. A duplicate descriptor changing `O_NONBLOCK` after admission therefore cannot bypass the deadline,
turn a full peer buffer into an immediate unclassified failure, or deliver `SIGPIPE` to the root process.

The transport returns bounded raw response bytes only together with an explicit indication that actual socket EOF was
observed; copying a complete-looking prefix into an in-memory reader cannot fabricate authority. The named capability
client decodes an EOF-qualified response with a non-cancelled context and lets either a valid success or valid remote
`DomainError` win over upload `EPIPE`, non-zero exit, or later reap diagnostics. Without one valid envelope, a pre-start
failure reports `process_started: false, outcome_unknown: false`; every post-start failure reports both values as true.

### Retained VM-exec authority-sidecar exception

The implemented and registered `jailer-vm-exec-session` action is the sole leased-lifetime exception to the
ordinary request/response rule above. It still uses the exact system binary, marker, action switch, sudo invocation,
and fd-0 AF_UNIX control socket. It handles one relay lease and exits; it is not a helper binary, daemon, generic
privileged channel, or second protocol listener. File descriptor 0 remains control-only. No `ExtraFiles`, `sudo -C`,
sudoers extension, environment input, caller path, raw command, or generic operation is permitted.

The normal `pkg/api` process opens and authenticates the existing source Firecracker connection. Only after it has read
the strict source request, resolved the exact destination, and allowed the directional policy does it start this action.
The initial closed request names the exact source/destination VM IDs and attaches exactly one source connection duplicate
with `SCM_RIGHTS` on the first request byte. After root pair admission, the normal process performs only the destination
Firecracker UDS `CONNECT` handshake, and a closed second phase attaches exactly one destination connection duplicate.
Every ancillary receive uses `MSG_CMSG_CLOEXEC`, rejects truncation and missing, extra, unknown, duplicate, or late
control messages, and proves one connected non-listening AF_UNIX stream. The action accepts no socket path, agent token,
target user, command, policy material, or response payload.

Root binds each live connection to its exact retained Firecracker record with `SO_PEERCRED`, `SO_PEERPIDFD`, PID/start
identity, complete active-process verification, and final liveness. Socket metadata proves the Firecracker peer, not
the selected guest port; the normal process's independent `SourceSession` token/bootstrap handshake proves the source
agent endpoint. Root reserves the exact active pair at the compiled host-global ceiling of eight, retains the
pair/capacity lease and both connection duplicates, and returns ready only after both FD proofs pass. Only after that
ready response may the normal process send the destination's token-and-command-bearing `DestinationRequest`; the
destination agent validates it before any effect.

The action-specific, closed, versioned session frames are bounded independently of ordinary `MVMRES01`; they cannot be
selected by another action. Explicit release, control EOF, caller crash, setup failure, or the absolute
`CLOCK_BOOTTIME` relay-stop deadline shuts down the shared connection descriptions and performs cancellation-detached
reverse cleanup before the child exits. The capacity record's four-second terminal/cleanup grace never extends
execution. A malformed or missing final outcome after process start remains outcome-unknown, and no retained authority
is inferred from process exit alone.

This exception preserves the ordinary transport unchanged for every other action. Production dispatch constructs the
retained server from the exact active-pair, global-capacity, Firecracker-peer, and absolute-stop authorities and
registers only `jailer-vm-exec-session`. The caller UID/GID passed to that server derives exclusively from the
authenticated control peer identity and never from request fields. Each source or destination descriptor remains an
opaque handler-owned capability, pinned and immutable through its sole synchronous binder call.

Authenticated failures that occur after control-channel structural admission but before action dispatch use the
action-specific `MVMXSES1` terminal failure, not ordinary `MVMRES01`, and do not drain request input. After dispatch,
the retained handler is the sole response and cleanup owner: it shuts down destination then source, releases the stop,
then releases destination/source peer pidfds before capacity, followed by process capabilities, active leases, and
pair roots. The registered action still has no API-owned relay listener/consumer; it receives no policy or relay
payload, and registration alone does not create a positive VM-to-VM path.

Receiver integration landed in two audit-friendly increments before any release action is registered. The first
increment admits only fd 0, sets and verifies close-on-exec, validates blocking `AF_UNIX`/`SOCK_STREAM` and
`SO_PEERCRED`, emits bounded early error envelopes only after structural channel admission and when a valid version-1
argv action is available, completes the response frame before `SHUT_WR`, and removes the obsolete standalone
EOF-delimited JSON decoder. A rejected closed action is not drained. The second increment adds closed, typed
trusted-release install/remove request and result values plus directly tested handlers. Install alone may consume its
declared payload through Jailer-owned exact-length and EOF admission; zero-payload install and remove require EOF before
their effects. Both handlers remained unregistered until the named Jailer client capability and its response-authority
tests completed in slice 6; they are now exact entries in the central switch.

### Implemented trusted-release handlers

Slice 5b implements the approved contract without registering either action. The two exact compiled internal actions
are `jailer-release-install` and `jailer-release-remove`. Their constants and all shared closed values live in
`internal/service/jailer`; they are exported only across Go's repository-local `internal` boundary and are not public
CLI or `pkg/api` interfaces. The closed shape is:

```go
const (
    TrustedReleaseInstallAction = "jailer-release-install"
    TrustedReleaseRemoveAction  = "jailer-release-remove"
)

type ReleaseSlot struct {
    Version      string `json:"version"`
    Architecture string `json:"architecture"`
}

type TrustedReleaseInstallRequest struct {
    Slot             ReleaseSlot `json:"slot"`
    AllowReplacement bool        `json:"allow_replacement"`
}

type TrustedReleaseRemoveRequest struct {
    Slot ReleaseSlot `json:"slot"`
}

type TrustedReleaseInstallOutcome string

const (
    TrustedReleaseInstalled TrustedReleaseInstallOutcome = "installed"
    TrustedReleaseReplaced  TrustedReleaseInstallOutcome = "replaced"
    TrustedReleaseUnchanged TrustedReleaseInstallOutcome = "unchanged"
)

type TrustedReleaseExecutableResult struct {
    SHA256    string `json:"sha256"`
    SizeBytes uint64 `json:"size_bytes"`
}

type TrustedReleaseInstallResult struct {
    Outcome       TrustedReleaseInstallOutcome   `json:"outcome"`
    Slot          ReleaseSlot                    `json:"slot"`
    ArchiveSHA256 string                         `json:"archive_sha256"`
    Firecracker   TrustedReleaseExecutableResult `json:"firecracker"`
    Jailer        TrustedReleaseExecutableResult `json:"jailer"`
}

type TrustedReleaseRemoveResult struct {
    Removed bool `json:"removed"`
}
```

The names, JSON fields, value domains, and action strings above are fixed. No request or result carries a path, URL,
caller hash, force flag, reference override, generic action, reader, or decoder field. The sole stream seam is:

```go
func (server *TrustedReleaseServer) Install(
    ctx context.Context,
    request TrustedReleaseInstallRequest,
    payload io.Reader,
    payloadLength uint64,
) (TrustedReleaseInstallResult, error)
```

The privileged adapter supplies one private deadline-aware raw-socket reader. Zero payload requires EOF before
`Install(ctx, request, nil, 0)`. Nonzero payload streams once through `Install`; existing Jailer archive-stage receive
exclusively owns declared-length and EOF admission. Anonymous staging may occur during the read, but no extraction,
canonical publication, or promotion of unadmitted bytes occurs before exact EOF. There is no 128 MiB buffer, second
stage, `io.LimitReader`, reusable reader interface, or replay.

One concrete `jailer.TrustedReleaseServer` owns the private `releaseAuthority` and exposes only named `Install` and
`Remove` methods. Privileged imports Jailer; the named Jailer client imports only `internal/lib/system` and
`internal/lib/privilegedwire`, never privileged. The server maps `AllowReplacement` to the existing closed intent and
converts only the fully re-admitted private manifest result into the exact result above. The
privileged package owns framing, deadlines, response delivery, and private exact install/remove function dependencies
for direct handler tests. There is no action registry, generic server interface, generic dispatcher, or decoder hook.

Each registered handler owns exactly one response transaction. Zero-payload install and remove require EOF before the
named effect. Nonzero install invokes `Install` once with the private stream; Jailer owns stream/EOF admission and no
canonical effect occurs before admission succeeds. The handler then emits exactly one typed success result or preserved
`DomainError` followed by `SHUT_WR`. Dispatch distinguishes an unhandled action from a handler-owned response failure,
so outer `run` never writes a second frame.

Each request reader carries the original operation context and one absolute deadline. It uses raw
`Recvmsg(MSG_DONTWAIT)` plus `POLLIN`, never `os.File.Read`, `SO_RCVTIMEO`, or mutable `O_NONBLOCK`. With cancellable
context, polling wakes and rechecks context at a compiled maximum 100 ms interval; uncancellable context may wait to the
absolute deadline. No individual cancellable poll waits longer than 100 ms, so cancellation never waits for the full
read deadline. The five-second header deadline starts immediately before decode. Nonzero install gets a separate
five-minute reader deadline after header decode for stream/EOF admission. Zero install/remove retain the header deadline
for EOF. The original context reaches Jailer; after EOF, the payload deadline does not constrain extraction/publication.
Install permits at most 128 MiB, remove permits zero, and the endpoint is never closed.

The response deadline is established immediately before each success or error delivery, not when the process or
receiver invocation starts. Final error delivery computes that deadline before `context.WithoutCancel` and retains the
earlier context deadline. The original `DomainError`, class, code, entity, and bounded postcommit details are preserved;
a response contains exactly one result or one error. Before success encode, require a valid three-value outcome, valid
slot exactly matching the request, lowercase 64-character archive/executable hashes, policy-valid executable sizes, and
exact nested values. The typed client repeats this semantic validation after decode. Remove Boolean is already closed.
Normal SQLite projection and postcommit retry acceptance belong to slice 7, not these handlers.

Focused L1 tests cover strict fields, types, nulls, duplicates, case conflicts, action mismatch, magic, schema,
truncation, and oversize; install zero/nonzero/oversize/truncated/trailing payloads; remove payload/trailing input; both
read deadlines, blocked-header/payload cancellation, and post-admission status mutation; zero/remove effects after EOF;
nonzero install once with publication only after Jailer admits EOF; all outcomes/remove Booleans; invalid fake effect
results; preserved `DomainError` details; response short writes, errors, half-close, and no double frame. The central
switch now registers only the two exact trusted-release actions; unknown actions remain rejected without reading.

### Authorization roles

The root-owned executable establishes code integrity. The `mvm` Unix group remains the authorization role for
passwordless privileged VM operations. Ordinary non-privileged commands do not require group membership.

Membership in `mvm` authorizes management of mvmctl-owned VM infrastructure; it does not authorize arbitrary host root
commands. The sudoers drop-in grants only the reserved privileged entry point of the root-owned system executable. It
does not grant the public CLI or raw `ip`, `iptables`, `iptables-restore`, `iptables-save`, `nft`, `modprobe`, or `sysctl`
commands.

`host init`, system-binary installation/replacement, group membership changes, sudoers changes, and `host reset` modify the
authorization boundary itself. They remain explicit administrator operations under the administrator's normal sudo
policy and are not exposed through the `mvm` group's passwordless dispatcher.

The approved administrator `host init` flow must support authenticated sudo and direct root with an explicit non-root
operator. A direct-root session must not guess that operator from a home/cache path or enroll root as the operator.
Selection, enrollment, early administrator dispatch, and root-owned mutation journaling remain implementation work.

The binary is never setuid and is not assigned broad Linux file capabilities.

### Typed privileged operation catalog

The initial dispatcher contains only the following named capabilities. Public callers retain domain-specific typed
methods; there is no generic privileged-operation interface.

| Capability | Allowed effect | Required binding |
|---|---|---|
| Trusted release install/remove | Verify and atomically manage an exact Firecracker/Jailer release pair | Fixed origin, version, architecture, root release manifest, active references |
| VM launch/abort/cleanup/reconcile | Create and recover one Jailer process, chroot, cgroup, and private mount namespace | Invoking UID, VM ID, exact release, root instance record, per-VM lock |
| Snapshot expose/remove | Mount one validated snapshot directory in the registered VM namespace | Invoking UID, VM ID, snapshot ID, pinned source/target descriptors |
| Volume expose/remove | Mount one validated volume at one typed drive ID in the registered VM namespace | Invoking UID, VM ID, volume/drive ID, pinned source/target descriptors |
| Image provision | Execute the existing typed provision operations inside one pinned managed image/rootfs | Invoking UID, managed resource identity, pinned root descriptor, bounded operation list |
| Bridge/TAP lifecycle | Create, configure, or remove an mvmctl-owned bridge or TAP | Invoking UID, network/VM identity, validated interface/address model |
| Neighbor invalidation | Delete only the dynamic guest-IPv4 neighbor on the registered managed bridge before host-veth exposure | Invoking UID, VM/endpoint identity, registered network, exact bridge and host namespace ([ADR-0021](0021-exact-managed-neighbor-invalidation.md)) |
| Firewall inspect/reconcile/teardown | Render and atomically apply the complete typed mvmctl ruleset | Invoking UID, typed firewall models, fixed mvmctl tables/chains/comments |
| Retained VM-exec session | Retain and peer-bind one exact source/destination connection pair under capacity and absolute-stop authority | Authenticated caller UID/GID, exact active VM identities and launch generations, pidfd-bound Firecracker peers |

Cgroup preparation and removal are part of VM launch/abort/cleanup rather than a public generic cgroup operation. Module
loading and sysctl mutation are administrator-owned host initialization steps, not operator dispatcher capabilities.

Adding a new privileged capability requires a new typed method, abuse cases, ADR-0016 review, and sudo threat-model
review. “Extensible for future use” is not a reason to add a generic action.

### Module placement and dependency direction

The privileged boundary follows the repository's existing service-subprocess architecture and does not create a second
application architecture:

| Package/file | Responsibility | Must not do |
|---|---|---|
| `cmd/mvm/main.go` | Detect the reserved marker and enter privileged dispatch before normal initialization | Parse domain requests, perform side effects, initialize the public CLI |
| `internal/service/privileged/` | Versioned envelope, bounded parsing, invoking identity, executable verification, and fixed action dispatch | Import `pkg/api`, `internal/cli`, or any `internal/core/*`; expose generic command execution or raw effect paths |
| `internal/service/jailer/` | Typed release, launch, namespace mount, cgroup, process, and cleanup handlers plus normal-user client calls | Orchestrate other core domains or trust user paths after validation |
| `internal/service/loopmount/` | Existing typed provisioning protocol and confined rootfs operations | Accept arbitrary host roots or unrelated unmount/PID targets |
| `internal/service/network/` | Typed root-side bridge, TAP, address, route, and neighbor mutations | Accept raw `ip` argv or own network business orchestration |
| `internal/service/firewall/` | Typed root-side firewall inspection and atomic managed-ruleset application | Accept raw nftables/iptables text from the caller |
| `internal/lib/authorityfs/` | Fixed descriptor-relative root-only ephemeral authority tree and closed named capability families | Import services, core domains, API, or CLI; expose raw paths/descriptors or generic lock names |
| `internal/lib/model/` | Shared typed request/value models used across boundaries | Import services, core domains, API, or CLI |
| `internal/lib/system/` | Subprocess transport and low-level process helpers | Become a generic privileged-operation API or render domain commands |
| `internal/core/{domain}/` | Existing domain logic and typed backend interfaces | Import another core domain or perform cross-domain orchestration |
| `pkg/api/` | Sole cross-core orchestration and public input validation | Implement root-side handlers or bypass typed service methods |

The central dispatcher performs only fixed routing and security-boundary checks. Actual effects remain in
capability-specific service packages and files. Each public client method keeps a domain name and shape, such as
`jailer.Launch`, `jailer.Cleanup`, `network.EnsureTap`, and `firewall.Reconcile`; there is no public
`ApplyOperations([]Operation)` or `RunCommand([]string)` method.

Where an existing leaf package needs privileged effects, it defines the smallest typed interface in the owning layer and
receives a concrete service client through construction. Leaf packages do not gain imports of `pkg/api`, `internal/cli`,
or core domains. The one existing loopmount service import exception is not generalized without a separate architecture
review.

Normal API `Input.Validate`/`Resolve` remains the caller-facing validation layer. Because the privileged dispatcher
receives data from an untrusted process, it independently enforces authorization, ownership, bounds, path confinement,
and system-damage invariants. These are receiver trust-boundary checks, not duplicated business validation.

### Implemented LoopMount client/protocol and rootfs-authority foundations

Task 13 now has a named normal-user client and closed protocol types for exactly three intended capabilities:
`ProvisionVM`, `InspectImage`, and `OptimizeImage`. The corresponding fixed action strings are
`loopmount-provision-vm`, `loopmount-inspect-image`, and `loopmount-optimize-image`. The client uses a private minimal
exchange seam and exposes no generic privileged call, decoder, executable, argv, command, shell, effect path, mount
target, or arbitrary operation list.

VM provisioning carries a canonical managed-cache locator, fixed-format VM ID, admitted rootfs size, closed filesystem,
and a typed plan. Image inspection and optimization carry the same namespace locator plus a fixed-format image ID,
admitted image size, closed filesystem, and, for optimization, a typed plan. VM resize is grow-only relative to the
admitted rootfs size, and a returned size must equal the requested resize or remain exactly unchanged when no resize was
requested. Image conversion is closed to ext4, and image shrink results cannot grow. Guest usernames are at most 32
bytes; SSH input is capped at 64 keys, 16 KiB per key, and 48 KiB total; agent tokens are canonical UUIDv4 values; and
agent ports are 1 through 65,535. Rootfs sizes are 128 MiB through 16 TiB, image sizes are 1 byte through 16 TiB, and
each result counter is at most 1,048,576. These validations are protocol admission only and do not make the cache
locator or resource identifiers root authority.

The client accepts a decoded success or remote `DomainError` only when the process actually started and the transport
observed authenticated socket EOF. A valid remote error preserves its code, class, entity, message, and bounded details
over later diagnostics. Every non-authoritative transport outcome uses `CodeProcessError`/`ClassInternal` with the fixed

### Release trust

The caller supplies a validated release version and architecture and may stream an exact-length bounded archive body for
cache efficiency. Privileged release code constructs the permitted Firecracker release and checksum URLs and obtains the
checksum independently from the fixed official origin with a dedicated bounded HTTPS-only client and proxies disabled.
It hashes the complete archive body against that checksum before parsing it. If no body is supplied, root uses the fixed
archive-fetch contract below. Root never opens a caller path or accepts a caller URL or checksum. The normal-user client
may read `MVM_ASSET_MIRROR`, but those streamed bytes are transport, never release authority.

Extraction reads the anonymous root-owned archive stage with bounded compressed/decompressed input and validates the
complete reviewed archive contract below before publishing any path. Only the exact Firecracker/Jailer pair is copied
to private root-owned staging descriptors. Their ELF class and machine must match the selected architecture without
executing downloaded code. The pair and strict root-owned release manifest are fsynced and atomically renamed into the
trusted store only after the complete archive and both executables pass admission. A referenced release cannot be
force-replaced.

ELF admission reads exactly the first 64 bytes of each extracted binary and performs no executable handoff. It requires
the ELF magic, ELF64 class, little-endian encoding, current ident/object versions, System V ABI version 0 with zero ident
padding, `ET_DYN`, a non-zero entry point, a 64-byte ELF header, program headers beginning at byte 64 with 56-byte
entries, and 1 through 64 program headers. Admission also receives the exact full-file size, enforces the 120-byte
through 64 MiB executable policy, and requires the complete declared program-header table to fit within that size. The
machine is exactly `EM_X86_64` (62) for `x86_64` or `EM_AARCH64` (183) for `aarch64`. A future upstream format change
fails closed until this reviewed policy and its tests are updated.

If upstream provides a stable verifiable signature or provenance mechanism, mvmctl should adopt it. Until then, the
fixed HTTPS origin and independently fetched checksum are an explicit supply-chain limitation, not a signature claim.

The receiver derives the source identity from the canonical release slot; none of these values are request fields. The
naming follows Firecracker's
[official binary-installation contract](https://github.com/firecracker-microvm/firecracker/blob/main/docs/getting-started.md#getting-a-firecracker-binary).

derivation is:

| Value | Receiver-derived form |
|---|---|
| Official origin | `https://github.com/firecracker-microvm/firecracker/releases/download` |
| Release tag | `v<version>` |
| Archive | `firecracker-v<version>-<architecture>.tgz` |

all-zero padding through gzip EOF. Non-zero padding, decompressed overflow, truncation, concatenated gzip members,

Trusted-store traversal starts at a pinned `/` descriptor and opens every fixed component with `O_NOFOLLOW` relative to
its retained parent. `/`, `/var`, and `/var/lib` must be root-owned directories without group or world write access.
Managed `/var/lib/mvmctl`, `binaries`, architecture, and version directories are exactly `root:root` mode `0700`.
`firecracker` and `jailer` are one-link root-owned regular files of mode `0755`; `manifest.json` is a one-link
root-owned regular file of mode `0600`. A missing architecture or version directory is an ordinary binary-not-found
result. Once the version directory exists, a missing or unsafe fixed leaf is an incomplete/corrupt trusted release and
fails as `binary.untrusted`, never as an absent release. Reads retain the version-directory descriptor, open each leaf
once, compare pre/post-read descriptor identity and metadata, and do not reconstruct a pathname.

Write-side store preparation never creates `/`, `/var`, or `/var/lib`. It may create only the fixed `mvmctl` and
`binaries` components relative to their already pinned parents, using mode `0700`, followed by descriptor-based owner,
group, type, and exact-mode verification. A component created by this call is explicitly set to `root:root 0700`; an
`EEXIST` result is treated as a concurrent creation and is verified without changing its metadata. After a newly
observed component is admitted, both that directory and its parent are fsynced before traversal continues. Symlink,
replacement, unsafe metadata, cancellation, and durability failures close all acquired descriptors in reverse order and
fail closed. This foundation creates no architecture/version slot and writes no archive or executable bytes.

Archive staging uses an anonymous regular file created on the pinned trusted-store filesystem with
`O_TMPFILE|O_EXCL|O_RDWR|O_CLOEXEC` relative to the `binaries` descriptor. It has no pathname and cannot later be linked
into the namespace. The descriptor must be `root:root`, exact mode `0600`, link count zero, and initially empty before it
can receive bytes. A filesystem without these anonymous-file semantics fails closed; there is no fallback to `/tmp`, a
visible random pathname, a replayable second stream, or a large in-memory archive. The stage is a private checked lease
and is not itself an installed release or executable authority.

Caller-supplied archive admission is a single-use transition on that stage. The declared body is 1 byte through
128 MiB; zero bytes select the separate root-fetch path and never represent an empty archive. Admission uses a fixed
32 KiB buffer and monotonically positioned writes so the descriptor offset remains zero. It consumes exactly the
declared bytes, hashes those same bytes once, and requires stream EOF with a one-byte probe; truncation, trailing data,
or disagreement with the independently fetched digest fails as untrusted input. Acceptance requires file `fsync`,
stable descriptor identity, exact post-write size and metadata, and an unchanged zero offset. Once stream consumption
starts, any failure poisons the stage and only checked release remains valid; failed bytes cannot be retried or parsed.

Executable admission opens the fixed `firecracker` and `jailer` leaves with `O_NOFOLLOW|O_NONBLOCK` relative to that
retained version-directory descriptor. The nonblocking open prevents an unsafe special-file leaf from stalling root
before type admission. Each descriptor must identify a one-link `root:root` regular file of exact mode `0755`, with a
size equal to its manifest entry and within the hard executable bound. Verification uses bounded positioned reads from
offset zero with a fixed 32 KiB buffer: it hashes exactly the declared bytes, captures the first 64 bytes for the closed
ELF policy, and probes the next byte so truncation and growth fail closed. Positioned reads leave the descriptor offset
unchanged. A second descriptor stat must match device, inode, type and mode, link count, owner and group, size,
modification time, and change time from the first stat. The service retains those same verified descriptors for the
later launch handoff; it never validates one pathname and executes a reopened pathname. Failure to admit `jailer`
closes an already admitted `firecracker`, and cleanup preserves the primary domain error while reporting any close
failure.

Installed-release preparation acquires the canonical release-slot lease before opening the trusted store or resolving
`manifest.json`. One private prepared value then owns that lease, the pinned store and version directory, the verified
manifest-derived release identity, and the exact admitted executable descriptors. Preparation failure releases acquired
resources in strict reverse order; successful release closes executables, version traversal, store traversal, and only
then the release-slot lease. Cleanup always uses a cancellation-independent context and preserves the primary domain
error while joining cleanup diagnostics. This slice exposes only preparation and checked release. Launch registration
remains deferred until the process-identity work can transfer the release lease and executable ownership together.

Trusted-release publication is one descriptor-relative directory transaction under that same release-slot lease. A
verified and fsynced architecture directory may remain empty after a failed or interrupted install; it is safe managed
structure, not an installed release. A candidate directory is exact `root:root` mode `0700` and uses the reserved,
slot-scoped name `.mvm-release-<slot-digest>-<nonce>.tmp`, where `<slot-digest>` is the 64-character lowercase SHA-256
used by the release-slot lock and `<nonce>` is 32 lowercase hexadecimal characters from 16 cryptographically random
bytes. The candidate contains only the fixed `firecracker`, `jailer`, and `manifest.json` leaves. Both finalized
anonymous executables are linked into it descriptor-relatively; the strict manifest is encoded, positioned-written,
and fsynced in an anonymous root-owned mode-`0600` descriptor without accepting a pathname. Production links each
anonymous object with descriptor-to-descriptor `linkat(..., AT_EMPTY_PATH)`; `/proc/self/fd` linkage exists only in
tests and is not a production authority path. Each linked file, the candidate directory, and the architecture directory
are fsynced in that order before commit. Every writable staging descriptor is checked closed before the complete exact
three-leaf candidate is re-admitted through its retained directory descriptor by the same manifest/executable read path
used for installed releases.

An install's `allow replacement` intent is permission, not a replace-only mode. An absent canonical slot installs
normally with or without that permission. An existing canonical version directory must contain exactly the three fixed
leaves and pass the shared strict manifest, full-file hash, and ELF admission before its canonical manifest may be
compared with a candidate. An exact canonical-manifest match is idempotent and reports unchanged with or without
replacement permission. It does not scan instance references because the release authority bytes and identity do not
change. A different existing release may be replaced only when the request explicitly allows replacement, the current
manifest and both executable leaves pass complete installed-release admission, and
`requireUnreferenced(current.releaseIdentity())` succeeds while the slot lease remains held. An unreadable, incomplete,
or corrupt installed slot always fails closed; replacement is not a repair bypass.

The private install result has one closed outcome: `installed`, `replaced`, or `unchanged`. It also carries the exact
release slot, archive digest, and executable digests and sizes from the fully re-admitted strict manifest. The manifest
metadata is the single source; the contract requires no redundant stored identity, and identity may be derived when
needed. The normal-user process consumes returned metadata and never reopens the root-owned mode-`0700` store.

Any precommit error returns a zero result. After an absent-install or replacement commit, the corresponding outcome and
metadata remain returned with any postcommit error. An unchanged result becomes authoritative only after the transaction
and its candidate cleanup complete; a candidate cleanup failure before that point returns a zero result and requires
retry. A later outer slot-lease release failure retains `unchanged` and its manifest metadata alongside the error.

An absent install commits with descriptor-relative `renameat2(RENAME_NOREPLACE)` from the reserved candidate name to
the canonical version leaf. A replacement commits with descriptor-relative `renameat2(RENAME_EXCHANGE)`, which moves
the old complete version directory to the reserved candidate name. Lack of either kernel operation is a host-capability
failure; there is no plain-rename, copy, per-file, or other non-atomic fallback. Successful rename/exchange is the
observable commit point. Any later error preserves the primary `DomainError` and adds `release_installed=true` or
`release_replaced=true`. Failure to fsync the architecture directory after that commit also adds
`durability_uncertain=true`; code never attempts to roll back a visible committed release. The successful absent rename
transitions the candidate capability to installed state before the post-commit parent fsync, and all later cleanup is
close-only so it cannot unlink canonical release leaves.

After a replacement commit and successful architecture-directory fsync, retirement unlinks only the three fixed leaves
through the retained old-directory descriptor, fsyncs that directory, removes the reserved directory, and fsyncs the
architecture directory again. Failure before the old directory is removed adds `retired_release_retained=true` and
does not disturb the new installed release. Failure of the final architecture fsync adds `durability_uncertain=true`.
Cancellation after commit follows the same state-reporting and cancellation-independent cleanup rules.

Before staging a new candidate, recovery under the same active release-slot lease scans only names with that slot's
exact reserved prefix. It requires the complete reserved-name grammar, opens each matching directory and leaf without
following links, and admits every matching candidate before the first unlink. A removable candidate is an exact
managed directory containing a subset of the three fixed leaves, each a root-owned regular file with its fixed mode,
one hard link, and bounded size. Any malformed matching name, unexpected entry, type, owner, mode, link count, size, or
unreadable state fails closed before cleanup and leaves every candidate for operator inspection.

Once cleanup begins it is cancellation-independent and resumable. For each admitted candidate, recovery unlinks only
the fixed leaves in a deterministic order, fsyncs the candidate directory, removes the now-empty directory, and fsyncs
the architecture directory. Admission records each reserved directory's device and inode. Recovery reopens its exact
reserved name and rechecks that binding immediately before the first leaf unlink and again before `rmdir`; a replaced
name is never deleted. A final architecture-directory fsync also runs when no candidate remains, allowing a retry to
confirm a prior removal whose final durability report failed. Recovery never recursively removes content. This covers
pre-commit candidates, post-exchange retired directories, and post-removal remnants without treating arbitrary
architecture-directory entries as disposable.

Atomic removal is a separate private transaction with this intentionally narrow interface:

```go
func (authority *releaseAuthority) removeInstalled(
    ctx context.Context,
    slot releaseSlot,
) (removed bool, err error)
```

The method accepts only a validated release slot. It accepts no path, URL, digest, force flag, reference bypass, or
generic operation. It acquires that slot's release lease before opening the store and retains the lease through final
cleanup and fsync. Read traversal is existing-only and never creates the store, architecture, or version directory. A
safely absent store or architecture is idempotent unchanged and performs no reference scan. Unsafe or unreadable state
fails closed.

Within an existing architecture, removal inspects the canonical name before recovery mutates any reserved remnant. If
the canonical version is safely absent, it runs matching-remnant recovery under the same lease and then returns
unchanged without a reference scan. If the canonical version exists, it must first contain exactly `manifest.json`,
`jailer`, and `firecracker`, pass the shared strict manifest, full-file hash, and ELF admission, reside on the
architecture directory's filesystem, and have its directory device and inode retained. A corrupt or unsafe canonical
release therefore causes zero recovery mutation. Only after that complete admission and identity binding succeeds does
removal recover matching reserved remnants under the same lease.

After recovery, the active slot lease passes the canonical release's exact manifest-derived identity to
`requireUnreferenced`; unreadable or corrupt reference authority fails closed. Immediately before commit, removal
reopens the canonical name, verifies its retained device/inode binding, and checks cancellation.

Removal generates only the exact slot-scoped reserved-name grammar above and validates every generated name. The
name-generation and no-replace-rename transaction permits at most eight total attempts: the first plus at most seven
retries. Only `EEXIST` from the no-replace rename is retryable; name generation, grammar validation, cancellation,
binding, and every other rename error fail immediately. The sole commit is descriptor-relative
`renameat2(RENAME_NOREPLACE)` from the canonical version name to one fresh reserved name within the pinned architecture
directory. Unsupported kernel semantics, cross-filesystem movement, or any other rename failure has no fallback to
plain rename, per-file movement, copying, or recursive removal. Rename success immediately transitions the private
removal target to committed, close-only state and fixes `removed=true` before any later fallible operation.

Post-commit work ignores cancellation and first fsyncs the architecture directory. It then closes the old executable
admission but continues best-effort cleanup if close fails, verifies that the reserved name still binds the retained old
directory, unlinks `manifest.json`, `jailer`, and `firecracker` in that fixed order through the retained directory
descriptor, and fsyncs that directory. It reverifies the reserved binding before `rmdir` and fsyncs the architecture
directory again after a successful removal. Leaf failures do not prevent later safe fixed-leaf cleanup, but `rmdir`
occurs only after the fixed leaves, old-directory fsync, and binding checks permit it. Target release is always
close-only; no release path may unlink the canonical name or a replacement reserved name.

Removal-owned rename, fsync, unlink, and `rmdir` failures use `CodeBinaryRemoveFailed` with `ClassInternal`. Shared
store admission and reference-authority `DomainError` values retain their original code, class, entity, details, and
wrapped cause; removal cleanup and annotations never recode them.

Every error after the rename preserves the primary `DomainError` and adds `release_removed=true`. Failure of the first
architecture fsync also adds `durability_uncertain=true` and `retired_release_retained=true`. A failure before `rmdir`
or a failed `rmdir` adds `retired_release_retained=true`; failure only at the final architecture fsync adds
`durability_uncertain=true` without claiming that the retired directory remains. Pre-commit errors add none of these
details because the canonical release remains installed.

The commit makes the canonical slot absent in one directory operation; it never exposes a partial canonical release. A
crash before commit leaves the complete canonical release. A crash after commit leaves the canonical slot absent and a
complete or safe fixed-leaf subset under the reserved name. A retry follows the same admission order: it admits an
existing canonical release before recovery, or recovers first and returns unchanged when canonical is safely absent. A
retry after `rmdir` still fsyncs the architecture directory to confirm durability. Corrupt recovery state always fails
closed for operator inspection. `RemoveAll`, pathname reconstruction, and recursive cleanup are prohibited.

### Paths, process identity, and runtime state

Privileged code treats the normal CLI, arguments, environment, database, cache, manifests, and downloaded content as
untrusted. Managed filesystem objects are opened once through descriptor-relative no-symlink resolution and retained as
pinned descriptors through each operation. Validation followed by pathname reopen is prohibited.

`MVM_CACHE_DIR` remains the user-selected location for persistent user state and large VM artifacts. The privileged
protocol may carry exactly one typed managed-cache locator; it is a namespace locator, not authority for an individual
effect. The receiver requires one canonical absolute path, rejects dot components, NULs, symlinks, magic links, unsafe
owners/modes, and unsupported mount topology, and pins the directory before resolving any resource. All subsequent
inputs are typed IDs, closed format enums, and presence/access intent. A request never supplies a kernel, rootfs,
snapshot, volume, config, PID, socket, log, mount-target, or temporary-file path.

The resource-bearing cache root must use a kernel-backed local filesystem from this closed set: ext2/ext3/ext4, XFS,
Btrfs, F2FS, bcachefs, tmpfs, or ZFS. FUSE, remote filesystems, overlay or other stacked filesystems, and automount cache
roots are rejected. The filesystem allowlist applies to the final pinned cache root, not `/` or unrelated ancestor
mounts. Every ancestor is still opened descriptor-relatively and checked for safe ownership, mode, and automount
topology. Bind, idmapped, shared, or private views of an approved underlying filesystem remain supported because their
authority comes from retained descriptors and exact identity checks, not the pathname or propagation mode.

Identity inspection requests synchronized `statx` metadata. It prefers `STATX_MNT_ID_UNIQUE`, records the identity kind,
and falls back to ordinary mount ID or explicit unavailability on older kernels. A later comparison includes the kind so
ordinary and unique mount identities are never treated as interchangeable.

This exception is deliberately narrower than a generic path interface. Dropping custom cache roots would break the
documented large-filesystem use case, while a persistent root-owned path registry would still need safe pathname
resolution after reboot. Instead, each live instance record binds the pinned cache root's stable identity (device,
inode, and mount identity where available). A later operation fails closed if it cannot re-pin the same cache identity.
Descendants are opened relative to that pinned root with beneath/no-symlink/no-magic-link resolution and retained until
the privileged effect and rollback are complete.

Privileged-visible basenames are canonical and derived by the receiver. Volume storage is keyed by volume ID rather
than user-visible name; the VM rootfs uses fixed `rootfs.img`; kernel and image names use their canonical IDs plus only
enumerated representations; cloud-init, Firecracker runtime, and snapshot leaves use compile-time fixed names. The user
database may describe a resource, but it cannot choose the basename root will open. Snapshot create exposes the snapshot
read-write and writes its fixed `rootfs.img`, `memory`, and `vmstate` leaves. Restore exposes the snapshot read-only and
overlays the new VM's pinned `/rootfs` at `/snapshot/rootfs.img` inside that VM's private mount namespace; no persistent
phantom-rootfs symlink is created.

Base VM launch admission uses a closed receiver policy before any descriptor is handed to the launch implementation.
The typed selection binds the VM ID, kernel ID, expected rootfs size, and a closed Firecracker launch intent. That
intent contains boot arguments, vCPU and memory values, SMT and dirty-page state, rootfs cache mode, guest MAC,
topology-derived TAP identity, cloud-init presence, logger and metrics presence, optional CPU configuration, and an
optional vsock CID. It contains no paths. Root derives every component and jail-visible path, then opens each resource
below the pinned cache descriptor with beneath/no-symlink/no-magic-link/no-cross-mount resolution. The base resource
limits are:

| Resource | Required size | Access and mode policy |
|---|---:|---|
| VM rootfs | 128 MiB through 16 TiB, exactly equal to the bounded expected size | Caller-owned, one-link regular file; owner read/write; no group/world write, execute, or special bits |
| Firecracker configuration | 1 byte through 1 MiB | Caller-owned, one-link regular file; owner read; no group/world write, execute, or special bits |
| Kernel | 1 byte through 1 GiB | Caller-owned, one-link regular file; owner read; execute bits permitted; no group/world write or special bits |
| Cloud-init ISO | 1 byte through 256 MiB | Caller-owned, one-link regular file; owner read; no group/world write, execute, or special bits |

The expected rootfs size is an equality check inside the receiver's hard range; it never raises the hard maximum. These
checks authorize only the base launch set. Snapshot restore, volume attachment, snapshot creation, output creation, and

#### Two-phase Jailer process authority

Firecracker Jailer 1.16.1 does not exec the trusted-store Firecracker inode directly. Its documented and implemented
lifecycle creates `<chroot-base>/<exec-name>/<id>/root`, copies `--exec-file` into that root, initially changes the copy
to the requested UID/GID, joins the requested network namespace, configures cgroups, unshares a new mount namespace,
bind-mounts and pivots to the jail root, prepares devices and directories, drops credentials, and finally execs the
copy. See the upstream [Jailer documentation](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/docs/jailer.md),
[`env.rs`](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/src/jailer/src/env.rs), and
[`chroot.rs`](https://github.com/firecracker-microvm/firecracker/blob/v1.16.1/src/jailer/src/chroot.rs).

Consequently, the trusted-store Firecracker device/inode can never equal `/proc/<pid>/exe`, and the final process root,
mount namespace, executable copy, cgroup observation, and dropped credentials do not exist before Jailer performs
effects. A one-phase record containing complete final identity before those effects is impossible. Jailer is invoked
without `--daemonize` and without `--new-pid-ns`, so the receiver-owned PID, start ticks, and pidfd continue to identify
one task while it changes from the blocked mvmctl child, to Jailer, to the copied Firecracker. Jailer's PID file and all
user-visible PID mirrors remain display evidence only.

The current strict instance-record schema version is 5, with this lifecycle:

```text
absent  ── registerLaunching ──> launching ── activateVerifiedProcess ──> active
cleaned ── registerLaunching ──> launching
launching ──── Abort ────> cleaning
active    ── BeginCleanup ──> cleaning
launching|active|cleaning ── recovery BeginCleanup ──> cleaning
cleaning  ───── Complete ─────> cleaned
```

The strict on-disk shape has these fixed fields; state-specific objects are omitted, not encoded with zero values:

| Scope | Exact fields | Present in |
|---|---|---|
| Record | `schema_version`, `owner_uid`, `vm_id`, `lifecycle`, `launch_generation`, `cleanup_generation` | Every state |
| `launch` | `owner_gid`, `network_placement`, `execution_identity`, `snapshot_id`, `cache_locator`, optional `output_identity`, `host_boot_id`, `pid`, `start_time_ticks`, `relay`, `managed_cache`, `release` | `launching`, `active`, `cleaning` |
| `launch.execution_identity` | `uid`, `gid` for the isolated execution account, distinct from the operator | Nested under `launch` |
| `launch.output_identity` | `log`, optional `metrics`, each with `device` and `inode` | Nested under `launch` when present |
| `launch.relay` | `kind`; when `present`, also `pid`, `start_time_ticks` | Nested under `launch` |
| `managed_cache` | `device_major`, `device_minor`, `inode`, `mount_identity.kind`, `mount_identity.id` | Nested under `launch` |
| `release` | `version`, `architecture`, `firecracker_sha256`, `jailer_sha256` | Nested under `launch` |
| `active` | `user_ids`, `group_ids`, `supplementary_groups`, `mount_namespace`, `jail_root`, `executable`, `relay` | `active`, and `cleaning` only after activation |
| `active.relay` | `kind`; when `present`, also `user_ids`, `group_ids`, `supplementary_groups`, `mount_namespace`, `root`, `executable` | Nested under `active` |
| Each credential set | `real`, `effective`, `saved`, `filesystem` | Nested under `active` |
| Each namespace/root identity | `device`, `inode` | Nested under `active` |
| `active.executable` | `device`, `inode`, `size_bytes`, `mode`, `uid`, `gid`, `links`, `manifest_sha256` | Nested under `active` |
| `active.relay.executable` | `device`, `inode`, `size_bytes`, `mode`, `uid`, `gid`, `links`, `sha256` | Nested under `active.relay` when present |

The strict codec rejects schemas 1 through 4, unknown or duplicate fields, missing required fields, and a state-specific
object that is present or absent in the wrong lifecycle. v0.3 performs no record migration or adoption.
Current launch admission requires an explicit, complete `managed` or endpoint-free `networkless` placement. Omitted,
unknown, and mixed shapes are rejected in launch and durable recovery; older cleaned tombstones are not adopted.
The networkless root lifecycle has a focused installed-candidate create/stop/start/vsock-exec smoke pass, not the full
Python or networked policy qualification.

`launching` is durable pre-effect intent, not a process-health claim. Fixed cgroup and jail paths are derived from the
VM ID and compiled constants; the exact cgroup membership and fixed jail metadata are verified rather than duplicated
as caller-shaped strings. The record has no cgroup path or cgroup object. It carries no caller path, raw descriptor,
Jailer argv, or fabricated final identity.

The relay field is an explicit closed union in both state-specific objects. `launch.relay.kind` is either `absent`,
with no locator fields, or `present`, with the handshake-blocked relay's PID and start ticks. `active.relay.kind` must
agree and is either `absent`, with no identity fields, or `present`, with receiver-observed UID and GID sets, the exact
empty supplementary-group set, host mount-namespace and host-root device/inode identities, and the relay executable's
device, inode, size, mode, owner, link count, and SHA-256. Every real/effective/saved/filesystem relay UID must equal the
authenticated caller UID and every GID must equal the authenticated caller GID. A present relay remains in the
receiver's host mount namespace with a root equal to the receiver's host `/` and executes the exact receiver-pinned
root-owned `/usr/local/bin/mvm` content. The record stores no socket path, PID-file path, raw descriptor, or argv.
`console.pid` and every other PID mirror remain display-only.

`active` retains that intent and adds receiver-observed final identity: every real/effective/saved/filesystem UID and
GID, the exact empty supplementary-group set, final mount-namespace device/inode, final
process-root/jail-root device/inode and fixed metadata, and the copied Firecracker's device/inode, exact size, mode,
owner, link count, and manifest digest. Every Firecracker process credential in `active.user_ids` and
`active.group_ids` must equal the respective recorded `launch.execution_identity` field, not the operator UID/GID.
The copied executable itself remains root-owned (`active.executable.uid` and `.gid` are zero). Rust's Unix
[`Command::uid`](https://doc.rust-lang.org/stable/std/os/unix/process/trait.CommandExt.html#tymethod.uid) calls
`setgroups(0, NULL)` when no groups are specified, and Jailer specifies none; v0.3 therefore requires an empty set
rather than accepting an arbitrary sorted set. Activation also requires exact membership in the derived cgroup.
For current managed launches, network namespace identity remains owned by the closed network topology capability and
is compared during activation without importing a raw path or descriptor into the record interface.

After dispatcher exit or crash, fresh recovery may re-admit a present relay only by opening a pidfd, matching boot ID,
PID, start ticks, every final credential, host namespace/root identity, and exact executable metadata and digest. A
missing or mismatched task is never signaled by PID; incomplete or ambiguous evidence returns `unavailable` and
preserves authority. A launching relay may be aborted only after its locator and expected blocked executable identity
are both proved. An absent relay requires no relay cleanup.

`cleaning` preserves the launch locator and any committed active identity required for exact cleanup. `cleaned` is the
persistent same-UID tombstone and retains only the record fields above; it carries no launch, cache, release, or process
identity. This is necessary because a managed cache's mount identity is valid only for one mount lifetime and cannot
authorize a relaunch after reboot. Release-reference scans treat `launching`, `active`, and `cleaning` as references.
`registerLaunching` starts `launch_generation` at one or increments the retained value exactly once; the first
transition into `cleaning` increments `cleanup_generation` exactly once, while repeated `BeginCleanup` calls preserve
it.

The activation order is fixed:

1. Spawn the Firecracker child and, when enabled, the dropped-caller console relay, each blocked on its own inherited
   private two-way handshake. EOF makes either child exit without exec or external effect.
2. Open the Firecracker-child pidfd and, when present, the relay pidfd, then send fresh parent challenges and require
   each still-blocked child to acknowledge before accepting PID-derived evidence. Read and recheck start ticks while
   each child remains blocked. A dead child cannot
   authenticate a reused PID, and a live acknowledged child cannot coexist with another task using that PID.
3. Consume the prepared release to atomically persist `launching` before output, mount, cgroup, link, namespace,
   chroot, or executable-handoff effects. The returned launch lease retains the release and VM locks, the Firecracker
   pidfd, the optional relay pidfd, and every later resource lease until it is consumed by activation or abort.
4. Under those locks, reconcile the exact derived Jailer destination
   `/var/lib/mvmctl/jailer/firecracker/<vm-id>`. Process absence must be proved before removing an exactly admitted,
   non-mounted stale fixed tree descriptor-relatively and bottom-up. Any unexpected entry, mount at or below the tree,
   replacement race, or incomplete admission returns `unavailable`; Jailer is not executed. Recheck the pinned parent
   and destination absence immediately before handoff. The authenticated root launch child then
   creates and pins the exclusive fresh VM/root tree before mounting resources and executing Jailer;
   a caller-created or previously existing tree is never adopted. This ordering adjustment was
   explicitly approved on 2026-09-19 because mounts require their fixed destination to exist.
   Prepare the separate fixed-name cgroup-v2 authority by descriptor-pinning `/sys/fs/cgroup`, its compiled `mvmctl`
   parent, and the `<vm-id>` leaf boundary with exact metadata and mount checks. The VM leaf must be freshly absent;
   an existing legacy leaf is never adopted. For a typed policy-v1 launch intent, require fixed `cpu`, `memory`, and
   `pids` controller readiness at the root and then the parent. Enable only missing controllers additively and verify
   each descriptor-relative readback; never disable an existing controller.
5. Prepare fixed outputs, the runtime directory, initial private mount namespace, and retained named mount sources.
   Do not create the final jail destination before the absence checkpoint. With the launch
   lease's VM lock already retained, acquire the later network mutation lock, then the host-global firewall mutation
   lock; create namespace-local and host links down; apply the complete nftables generation atomically and verify it
   through a fresh inspection. Only after firewall success may the exact links be raised and reverified. Both mutation
   locks remain held through this activation checkpoint. A failure before their successful release keeps or lowers
   links and leaves both children blocked while typed abort unwinds with the same locks. After successful activation,
   release the firewall then network mutation lock while the opaque topology and verified endpoint authority remain.
6. Release the relay, observe and record its exact caller credentials, empty supplementary groups, host mount
   namespace/root, root-owned `/usr/local/bin/mvm` executable metadata and digest, and verify readiness.
7. Recheck the pinned release, fresh jail-destination absence, cgroup-leaf absence, and root-then-parent controller
   readiness at the last handoff boundary, then release the authenticated Firecracker child. It creates
   and descriptor-pins the exclusive fresh jail tree, attaches only the root-parent-prepared fixed-name detached
   mounts, and executes the exact Jailer with the pinned network namespace. The root parent materializes the sealed
   configuration in a private read-only tmpfs and retains the original source descriptors for attestation; the child
   re-pins the fixed jail parent in its own mount namespace before attaching resources.
   No existing tree, caller-supplied path, or generic command can substitute for this transition.
   Record successful
   Jailer-handoff provenance in the retained cgroup authority before it may bind the resulting leaf. The prepared
   release supplies the fixed store paths; the caller supplies neither a hash nor path. This release occurs only after
   the complete firewall generation and links are verified.
8. Retain the original pidfd for stable task identity and exit detection while bounded, context-aware observation
   waits for both Jailer's isolated-owner private root and copied executable before binding their pre-seal identity.
   It then repeatedly opens and verifies `/proc/<pid>/exe` until it is the copied Firecracker rather than transient Jailer
   state. Each poll matches the pinned root and executable before reading final credentials, so it cannot combine
   pre-exec Jailer credentials with post-exec Firecracker objects. A matching final task must still pass the strict
   credential checks; invalid final credentials are not a retryable transition. The compiled observation budget is
   10 seconds with a 25-millisecond minimum interval; an earlier context
   deadline wins. Each interval checks the pidfd nonblocking for exit and rechecks boot ID, PID, and start ticks. An
   exited pidfd ends observation immediately. A pidfd becomes readable for exit, not for `exec`, so it is never used as
   an executable-transition notification; see [`pidfd_open(2)`](https://man7.org/linux/man-pages/man2/pidfd_open.2.html).
   No busy or unbounded loop is permitted.
9. Open the derived jail root descriptor-relatively. Require the host jail-root leaf and `/proc/<pid>/root` to be the
   same device/inode, and require its fixed `firecracker` leaf to be the same inode as `/proc/<pid>/exe`.
10. Change the final jail root and copied executable to exact `root:root` mode `0755`, beneath exact `root:root` mode
   `0700` Jailer base and per-VM ancestors. Hash the sealed copy against the exact release manifest and recheck metadata.
11. Re-observe boot ID, PID/start ticks, credentials, empty groups, cgroup, namespaces, root, executable, relay identity,
    and pidfd liveness. Before membership, descriptor-relatively read back exact policy-v1 `cpu.max`, `cpu.weight`,
    `memory.high`, `memory.max`, `memory.swap.max`, and `pids.max` values. Then prove through the retained cgroup
    authority that the pidfd/start-tick-bound task is the exact leaf's sole member. A failed limit or membership proof
    preserves that same lease, and retry repeats both. Then atomically replace `launching` with `active`.

The v0.3.0 public network/NAT request carries only whether NAT is enabled. It exposes no `NATGateways`, uplink name,
ifindex, route, or selector. When NAT is enabled, root discovers exactly one eligible IPv4 main-table default-route
uplink through its typed, host-network-namespace-bound rtnetlink authority. An eligible route is unicast `0.0.0.0/0`,
has one output interface and no multipath next hops, and resolves to a non-loopback, non-mvm-owned link. Root persists
the exact ifindex, name, kind, and host network-namespace identity, then revalidates the route and link before firewall
compilation, application, and topology activation. Zero eligible uplinks, multiple eligible uplinks regardless of
metric, replacement, or changed identity fails closed. Multi-uplink selection is unsupported in v0.3.0. Removing the
current public input/model surface, replacing the compiler's raw uplink string with the retained typed identity, and
adding L1/L2 coverage remain pending; this decision does not claim those code changes.

Sealing makes the copied inode immutable to the dropped caller and preserves the exact-content proof established at
activation. Later status batches can compare the root-owned inode and metadata without rehashing every executable;
release installation/removal still uses the exact manifest and release-reference locks. A process becoming `active`
proves final launch identity, not Firecracker API, SSH, or guest-agent readiness.

The blocked console relay remains in the host mount namespace and receives only inherited PTY, pinned log, and pinned
runtime-directory descriptors. It never reopens a caller path or retains the VM namespace. Live snapshot and volume
operations reopen the final `/proc/<pid>/ns/mnt` after verifying active identity; no pre-Jailer or persistent namespace
descriptor is treated as the final namespace.

Every resource-owning composite lease, including launch, active, cleanup, release-slot, authority-root, and UID-directory
leases, uses pointer-shared mutex-protected lifecycle state. Checked release runs once across copies and concurrent
callers, ignores cancellation while preserving context values, and caches and repeats the first cleanup result. It
never retries an unlock or close against a descriptor number that the kernel may have reused. This matches the closed
`authorityfs` capabilities and `verifiedProcessLease`; it does not add a generic callback, raw fd, or raw path seam.

The ordinary privileged dispatcher remains synchronous and short-lived. Once both instance
and topology are durably active and their recovery metadata is complete, a distinct successful
detach closes operation-local descriptors and locks without stopping the VM or dismantling its
resources. Root-owned records and the namespace's root-owned nsfs mount retain lifetime
responsibility. Later status, exec, stop, and recovery calls reacquire the locks and re-admit
exact persisted identities; no user SQLite value substitutes for those records. A failed or
durability-uncertain activation cannot detach. The network capability must implement exact
same-boot reopening before this path is enabled; see ADR-0017's retained activation authority.

The private child transport adds two narrow subprocess-boundary exceptions: fixed-binary
`os.StartProcess` in `lifecycle_child_spawn.go` creates the authenticated handshake-blocked child,
and `syscall.Exec` in `lifecycle_child.go` performs the fixed admitted Jailer handoff after
descriptor-only mount preparation. Neither accepts a caller-supplied executable or generic
command. The reserved early child route exits the process on every outcome and never returns
its namespace-bound thread to ordinary application initialization.

`launchLease.Abort(ctx)` and `activeLease.BeginCleanup(ctx)` are consuming transitions. They atomically move the held
release reference and slot lock, VM lock, pidfds, and every acquired output, mount, topology, and firewall endpoint
resource lease, including the fixed-name cgroup authority, into one `cleanupLease`; the source lease becomes inert.
Abort may call the cgroup authority's causal `BindForCleanup` only after the exact retained task has been terminated
and reaped. A post-registration error never releases and
reacquires the VM lock before cleaning. `instanceAuthority.BeginCleanup(ctx, caller, vmID)` exists only for a fresh
dispatcher performing recovery admission and reacquires the exact record and locks in global order. It is not the
error-path transition for a live launch or active lease. There is one named `Abort` method, not interchangeable aliases
or a generic state transition. Once activation has released its mutation locks, later stop, failure, or recovery
cleanup reacquires the per-network lock and then the host-global firewall lock under the retained or freshly admitted
VM lock. Active lifetime authority never holds either mutation lock and therefore does not serialize unrelated VMs.

Every durable transition has a typed commit result. Before rename, registration returns no launch lease and leaves the
prepared release live; activation returns no active lease and leaves the launch lease live. Once the launching rename
succeeds, registration transfers in-memory ownership to a non-nil launch lease before any later parent-directory
`fsync` or checked close. Once the active rename succeeds, activation likewise transfers ownership to a non-nil active
lease first. Those post-rename failures return that lease together with a `DomainError` carrying
`record_replaced=true` and, when persistence is uncertain, `durability_uncertain=true`. The caller invokes
`launchLease.Abort` or `activeLease.BeginCleanup` through the returned authority, preserves the primary error plus
bounded cleanup diagnostics, and never acts through the stale source lease. No process, VM, release, network, or
firewall authority is dropped between a failed pre-release activation checkpoint and cleaning; the network and
firewall mutation locks remain held. After a fully successful activation checkpoint, the firewall then network
mutation lock release normally; the active lease retains only the topology and endpoint authority needed to reacquire
them in canonical order for later cleanup.

Live snapshot and volume operations reopen and verify `/proc/<pid>/ns/mnt` while the process is alive and enter only
that namespace. No persistent mount-namespace handle is retained after the operation, because doing so would retain
every mount after process exit. Cleanup stops and reaps the verified relay, unmounts named resources in reverse order,
unlinks only the five fixed runtime leaves, and removes the runtime directory only when empty. It preserves persistent
outputs and never recursively traverses a caller-writable tree or a tree that may contain a mount. Unexpected runtime
entries leave a bounded recoverable cleanup record instead of authorizing recursive deletion.

### Failure and reconciliation contract

A durable `launching` record exists before the first externally mutable privileged launch side effect. A blocked child
may exist first only while an inherited private handshake makes external mutation impossible and EOF forces exit.
Every post-registration failure retains a live lifecycle handle and invokes a typed abort that verifies the persistent
VM and optional relay PID/start locators, terminates either process only through its separately verified pidfd, checks
cgroup emptiness through retained private authority, and cleans namespace/chroot/instance state in order. A fresh
dispatcher can now recover that cgroup authority for an exact active or launching task, or prove stable absence across
a boot mismatch, before cleanup continues. Same-boot dead-process cgroup reconciliation remains pending.

Startup and pre-launch reconciliation compare root instance records, processes, cgroups, and chroot directories. They do
not trust the user database as root authorization. Operations are idempotent and either converge to a known state or
return a precise error without deleting potentially mounted user data.

Read-side status is also reconciled. Before `mvm vm ls`, `mvm vm ps`, or `mvm vm inspect` filters or renders a status,
the normal process obtains one bounded typed batch observation from root authority. Its closed outcomes are `running`,
`stopped`, `crashed`, and `unavailable`: an absent/cleaned record or host boot-ID mismatch is `stopped`; a same-boot
missing, dead, or mismatched active process is `crashed`; and a permission, I/O, corrupt-record, missing-capability, or
incomplete authoritative inspection is `unavailable`. Stopped and crashed are successful observations, not internal
errors. Any unavailable item fails the complete read rather than returning a partial or stale projection.

Implementation note (2026-09-13): the private schema-3 batch observer implements those classifications for at most
1,000 canonical unique VM IDs, using one ownership-index scan and at most one VM lock/process set at a time. Active
observation retains pidfds across two descriptor-pinned metadata reads and a final liveness sweep without rehashing
executables. It compares the persisted mount namespace, root, executable metadata, credentials, and derived cgroup
path. Network namespace identity is only compared between observations; schema 3 does not persist it, so this is not
proof of the expected topology namespace. Same-boot `launching` and `cleaning` return unavailable. The observer neither
signals nor repairs state and returns no partial map on failure. Public status remains unwired until the schema-3
lifecycle writer and required recovery are composed. L1 benchmarks use real record files with fake process/lock effects,
one owner, and no relays; they do not qualify live 1,000-VM or host-reboot behavior.

Reconciliation handles an interrupted `launching` record by exact case. A boot mismatch becomes stopped and cleans
fixed artifacts without signaling. A same-boot missing PID or start-tick mismatch becomes crashed and never signals the
current PID. The exact same task already running the final copied Firecracker may complete the idempotent seal,
reverification, and `active` commit. The exact same task still in Jailer, another transient exec state, or a mismatched
exec is terminated only through its verified pidfd and proceeds to cleaning. A present relay is separately re-admitted
through its locator and complete state-appropriate identity; `console.pid` is never read for authority. A boot
mismatch, missing relay, or locator mismatch never signals any current PID. If either process cannot be classified,
recovery returns unavailable and neither guesses nor deletes ambiguous state. `cleaning` always resumes idempotently.

| Durable state and observation | Required recovery | Outcome returned by that recovery pass |
|---|---|---|
| `launching`, host boot mismatch | Do not signal; clean fixed host artifacts and commit `cleaned` | `stopped` |
| `launching`, PID absent or start mismatch | Do not signal any current PID; clean fixed artifacts and commit `cleaned` | `crashed` |
| `launching`, exact task and optional relay prove final identities | Finish sealing and verification, then commit `active` | `running` |
| `launching`, exact task is Jailer/transient/wrong exec and optional relay is exactly admitted | Terminate only through verified pidfds, then clean | `crashed` |
| `active`, host boot mismatch | Do not signal; reconcile fixed artifacts to `cleaned` | `stopped` |
| `active`, same-boot VM or present relay absent/dead/identity mismatch | Do not signal an unverified task; reconcile through `cleaning` | `crashed` |
| `cleaning` | Resume the recorded cleanup generation idempotently | `stopped` |
| Any state that cannot be classified completely | Preserve authority and perform no guessed kill/delete | `unavailable`; fail the read |

The read path never opens one sudo process per VM and never dials the Firecracker API or guest agent as a liveness tick.
It may update the user database as a projection only after it receives a complete authoritative result; SQLite remains
non-authoritative.

The target contract is that every create, start, reboot, and snapshot-restore path prepares the same complete typed
relaunch state. If the VM has a persisted vsock configuration, the root launch request includes only its validated CID;
root derives the fixed runtime UDS leaf. The normal process retains the agent port and token for the post-launch client
probe instead of exposing them to root. A repository failure aborts launch instead of silently omitting the device.
Root removes an old fixed vsock socket only after authority proves that no live active or recoverable launching process
owns it.

Snapshot restore additionally preserves the trusted snapshot-captured network ID, guest IPv4 address, and guest MAC;
those values are part of the guest's embedded network state rather than fresh allocation inputs. Root must admit
trusted snapshot metadata, reserve that exact endpoint for the restored VM, and fail before launch when the address or
MAC conflicts, the source VM still owns the endpoint, or the requested destination network differs. v0.3.0 does not
support fresh IP/MAC allocation during restore, cross-network restore, or a simultaneous endpoint clone. The new VM's
derived host TAP name may differ, but the firewall anti-spoof endpoint must use the captured guest address and MAC.
Root-owned snapshot network metadata, restore composition, conflict tests, and live snapshot qualification remain
pending; user SQLite rows or caller-supplied snapshot metadata never authorize the reservation.

## Alternatives Considered

### Separate privileged helper binary

This provides the smallest executable trust boundary, but creates a second artifact and contradicts the product's
single-binary contract. Rejected in favor of early dispatch within one immutable system installation.

### User-owned CLI with a sudo command digest

Pinning a digest would make every user update require sudoers regeneration and would retain a user-owned path at the
root boundary. It also leaves the public CLI initialization path exposed to root execution. Rejected.

### Continue wildcard sudo for a root-owned public CLI

Root ownership fixes executable replacement but `mvm *` would still allow every public command to run as root and load
user state under root authority. Rejected. Only the reserved early dispatcher is allowed.

### Setuid or broad file capabilities

Both would expose privilege on every invocation and make the whole public CLI a security boundary. Required operations
also span mount, network, cgroup, and process privileges that do not reduce cleanly to a safe fixed capability set.
Rejected.

### One-phase complete process identity

Recording the trusted-store inode or the pre-Jailer mount namespace as final identity would describe a process that
cannot exist: Jailer creates a different executable inode and pivots into a later namespace. Fabricating either value,
or performing Jailer effects before any durable record exists, fails closed recovery. Rejected in favor of durable
`launching` intent followed by receiver-observed `active` identity.

### Jailer PID files, daemonization, or a new PID namespace

Jailer's PID file and caller-visible PID mirrors are replaceable display evidence, while daemonization or a new PID
namespace would break the original PID/start/pidfd continuity used by the authority record. Rejected; the blocked child
execs Jailer and Firecracker as one pidfd-pinned task.

### Root daemon, polkit service, or systemd RPC

These can provide a strong authorization boundary but add a long-running service, protocol lifecycle, and additional
deployment artifacts. Rejected for the initial implementation; reconsider only if concurrency or policy needs exceed the
short-lived dispatcher model.

## Consequences

**Benefits:**

- The product retains one compiled and installed executable.
- Passwordless sudo can no longer execute user-selected program bytes or raw host-tool arguments.
- Root execution bypasses user configuration and the ordinary CLI initialization graph.
- The `mvm` group has a precise meaning: authorized mvmctl operator, not unrestricted root.
- Privileged state and user state have explicit owners and recovery responsibilities.

**Costs and limitations:**

- Installation and system-binary replacement require an explicit administrator step.
- Development binaries cannot perform privileged work unless a compatible system binary is installed.
- All raw privileged callsites must be replaced by typed operations before the final sudoers policy is enabled.
- The single executable contains more code than a dedicated helper, so early dispatch and import-graph isolation require
  strict tests and review.
- Multi-user ownership, crash recovery, release verification, namespace mounts, and firewall atomicity add implementation
  and L2 testing cost.

## Clean Installation and Release Gate

ADR-0005 remains a historical description of the pre-v0.3 policy. v0.3.0 provides no compatibility or automated
migration path for that policy, its user state, or its runtime resources. The implementation and release sequence is:

1. Add early privileged dispatch, the exact administrator bootstrap route, and negative tests while the final marker-only
   path is unreachable from sudoers.
2. Replace every supported privileged service/tool call with a typed operation.
3. On a clean host, install the trusted artifact as the root-owned system binary and atomically activate only the
   marker-scoped sudoers drop-in after `visudo` validation.
4. Run installation, replacement, privilege-abuse, multi-user, path-race, PID-reuse, crash-recovery, Jailer, cgroup,
   snapshot, hotplug, and firewall L2 tests through the installed binary.
5. Mark ADR-0005 superseded for v0.3.0, update all current-behavior documentation, and only then describe the new
   boundary as active.

No implementation phase is complete while documentation describes a different executable path, sudo policy, state
location, lifecycle guarantee, or known limitation.
